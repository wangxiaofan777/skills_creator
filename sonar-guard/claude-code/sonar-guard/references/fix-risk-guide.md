# 修复风险评估指南(fix-risk-guide)

回答用户最关心的问题:**"按 Sonar 的建议改,会不会把功能改坏?"**
给任何修复建议前,先按本指南给出风险等级、理由和验证方案。

## 风险等级定义

| 等级 | 含义 | 处理方式 |
|---|---|---|
| 🟢 零/低风险 | 修复不改变程序运行时行为,或改变可被编译器/类型系统完全保证 | 直接修,无需确认 |
| 🟡 中风险 | 修复在绝大多数情况下安全,但在特定边界条件下可能改变行为 | 修复前确认测试覆盖,修后跑相关测试,报告中写明潜在变化点 |
| 🔴 高风险 | 修复本质上是在**改变程序行为**(这往往正是规则的目的——原行为是 bug),改对了是修 bug,改错了是引入 bug | 必须先向用户说明行为将如何变化,确认后再改;单独提交 |

## 按修复类型分级

### 🟢 零/低风险(行为不变)

- 删除未使用的 import、局部变量、私有方法(**注意例外**:被反射、序列化框架、依赖注入容器使用的"看似未用"成员——Java 项目里看到 `@Autowired`、`@Value`、JSON 序列化字段时升级为 🟡)
- 重命名局部变量/私有成员以符合命名规范(public API 重命名是 🔴,会破坏调用方)
- 魔法数字提取为常量(值不变)
- 重复字符串字面量提取为常量
- 补充 `@Override`、`final` 修饰符(若编译通过)
- 删除注释掉的代码块
- 降低圈复杂度的**纯提取函数**重构(逻辑逐行搬运,不"顺手优化")
- `==` 改 `===`(JS/TS)且两侧类型确定相同时
- f-string / 模板字符串替换字符串拼接(输出逐字符相同时)

### 🟡 中风险(边界条件下可能变化)

- **资源关闭**(try-with-resources / with / defer Close):主路径不变,但异常路径上关闭时机改变;若原代码"依赖"未关闭(罕见但存在,如复用流),会出问题 → 验证:跑涉及该资源的集成测试
- **集合判空方式调整**(`isEmpty()` 替代 `size()==0` 等):语义等价,但自定义集合类可能重写不一致
- **StringBuilder 替换循环字符串拼接**:结果相同,但要确认拼接逻辑没有依赖中间值
- **日志替换 System.out/print**:输出去向变了;若有脚本在解析 stdout,会受影响 → 问一句"有没有外部依赖这个输出"
- **`Optional`/空安全包装重构**:链路等价改写一般安全,但 `orElse` vs `orElseGet` 有求值时机差异
- **JS `==` 改 `===` 且涉及 null/undefined 比较**:`x == null` 同时匹配 null 和 undefined,改成 `x === null` 会漏掉 undefined → 应改为 `x === null || x === undefined` 或保留并加注释豁免
- **Vue/React 列表 key 修正**(index 改唯一 id):修复了复用 bug,但若组件内部状态依赖旧的复用行为,渲染表现会变
- **依赖升级类修复**(漏洞版本升级):API 兼容时低风险,跨主版本时升级为 🔴

### 🔴 高风险(修复=改变行为)

- **空 catch 块/裸 except 补处理**:原来异常被吞掉、程序继续跑;补上日志是 🟢,但**改成抛出或返回错误**会让原本"带病运行"的路径开始失败——这可能正确,但必须让用户决定
- **空指针/None 防御**:加 null 检查后,原本会 NPE 崩溃的路径变成静默跳过或提前返回——崩溃是显性 bug,静默跳过可能是隐性 bug,需要用户确认期望行为
- **equals/hashCode 修正**:影响所有 HashMap/HashSet/去重/缓存行为
- **并发类修复**(加锁、volatile、ConcurrentHashMap 替换、double-checked locking 修正):正确性提升但可能引入死锁或性能变化;必须了解调用场景
- **SQL 注入修复(参数化)**:语义上应当等价,但动态拼接 ORDER BY/表名无法参数化,需要白名单方案,改法不当会直接报错
- **正则修改**(修 ReDoS 或逻辑):正则极易改出匹配差异,必须用原有用例+新增用例双向验证
- **浮点比较修正**(== 改 epsilon 比较):阈值选择影响业务判断
- **异常类型收窄**(catch Exception 改 catch 具体异常):未列入的异常将向上抛出,改变错误处理路径
- **public API 任何签名/命名变更**
- **安全相关行为变更**(关闭的证书校验重新打开、弱加密算法替换):必须改,但很可能直接导致与旧系统的联调失败,需要协调

## 报告模板(每个修复建议都按此给出)

```
- 风险等级: 🟡 中
- 行为变化点: 异常发生时连接将被立即释放(原来泄漏到 GC)
- 改坏的可能场景: 若调用方在 catch 后仍使用该连接(代码坏味道, 已检查本文件无此用法)
- 验证方案: 运行 OrderServiceTest, 重点看异常分支用例
```

## 通用原则

1. **没有测试覆盖的 🟡/🔴 修复,先建议补测试再修**,或明确告知用户"此处无测试,修复后无法自动验证"。
2. **批量修复按风险分组、分批提交**:一次提交里只放同一风险级别的修复,出问题好回滚、好定位。
3. **不要"顺手优化"**:修 Sonar 问题时只做规则要求的最小变更,任何额外重构单独提出。
4. **存量老代码的 🔴 问题**:默认建议"标记 Won't Fix / 加豁免注释 + 排期重构",而不是上线前夕大改。Sonar 支持在界面上标记,或用 `@SuppressWarnings("java:Sxxxx")` / `// NOSONAR` (需团队规范允许)。
5. 修复后让用户跑:单元测试 → 该模块集成测试 → (高风险时)回归核心链路。
